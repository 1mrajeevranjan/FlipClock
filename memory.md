# FlipClock Project Memory

Non-obvious lessons learned building this app — the "why" behind decisions that would otherwise look arbitrary or wrong on a second read. `CLAUDE.md`'s Known Gotchas is the condensed/authoritative version for AI agents working in this repo; this file has more narrative context behind each one.

## AppKit/SwiftUI interop surprises

- **`.preferredColorScheme()` doesn't reliably re-propagate to `@Environment(\.colorScheme)` reads on *updates* when the view is hosted inside an `NSStatusItem` button.** Discovered while building the reminder pulse: a plain `NSHostingView.rootView` reassignment and a `TimelineView` both changed SwiftUI's internal state correctly (verified via logging — the state genuinely toggled every 5s) but the status item never visually repainted. A diagnostic background-color toggle, driven through the *exact same* rootView-reassignment mechanism, updated fine — narrowing the bug specifically to `.preferredColorScheme()`'s environment propagation, not the update mechanism itself. Fix: `SplitFlapClockFace.isDarkOverride: Bool?`, an explicit view *parameter* that bypasses the environment entirely. Also needed `statusItem.button?.needsDisplay = true` forced alongside the rootView swap — `NSStatusBarButton` composites through a separate (SkyLight) pipeline that isn't part of a normal window's live-updating render loop.

- **A `.popover()` triggered from inside content that's already itself presented as a popover doesn't reliably present.** `CalendarMonthView` lives inside `PopoverClockView`, which is hosted via `NSPopover`. A nested `.popover()` for the hover-preview card silently did nothing — no crash, no log, just never appeared, even confirmed via multiple live-hover attempts. Fixed by using a plain inline `.overlay()` instead — content in the same view tree, not a second presentation layer, so it can't fail that way.

- **`NSVisualEffectView.behindWindow` blending stops re-sampling the desktop once fully covered** (e.g. by an opaque `CALayer` animating on top of it) and doesn't resume on its own. Confirmed by pixel-sampling a screen recording: the same card position froze at one flat color for 200ms+ after a flip landed. Fix pattern (from the pre-reminders era, before the card style moved to opaque frosted tone): toggle `.state = .inactive` then `.active` right when whatever was covering it goes away.

- **`NSWindow.frame` truncates to whole points.** Any per-tick animation accumulating a sub-pixel offset (float-across-screen drift) must track its own precise `CGPoint` and only ever *write* to `window.frame`, never read the accumulator back from it.

- **`SettingsView`'s tab-selection pill "bounced" on some tab switches (General↔Appearance) but slid cleanly on others (Appearance↔Desktop Clock)** — a real bug that survived several rounds of fixes because each one targeted a plausible-looking but wrong cause. Tried, in order: (1) a shared `matchedGeometryEffect` pill — fixed an earlier "four rectangles cross-fading" bug but introduced its own artifact (the pill vanished for 2 frames then popped in mid-slide, confirmed by tracking its x-position frame-by-frame in a real 30fps screen recording); (2) restructuring the header from `.overlay()` into a `ZStack` sibling of the card content, on the theory that `.overlay()`'s placement deriving from the resizing content view was destabilizing the geometry match — measurably fixed the vanish/pop, but the user still saw a bounce; (3) an animated `NSWindow` resize with the hosting view pinned via `.minYMargin` — made it *worse* (`NSHostingView` ignores `autoresizingMask`, it uses Auto Layout). The actual cause only showed up when tracking the pill's full bounding box (x, y, width, *and* height, not just x) at 60fps: its y-position was dipping ~39pt and its height squashing ~79→46px during the transition, arcing diagonally down-right before recovering — because `.animation(_:value:)` (and `matchedGeometryEffect`, for the same underlying reason) animates *every* animatable change in its subtree, not just the one you're thinking about, so a transient layout re-resolution during a big content-height change got eased right along with the intended horizontal slide. Fix: a plain `@State private var pillX: CGFloat`, mutated inside `withAnimation` in the button's own action (not via a `.animation(_:value:)` modifier anywhere), with `selectedTab` itself assigned *outside* that transaction. One scalar animates; nothing else can. The window resize was also switched to unanimated (`animate: false`) since an animated `NSWindow` frame independently misplaces top-aligned `NSHostingView` content while it grows (see `CLAUDE.md` gotcha). Lesson for next time a SwiftUI animation looks inconsistent across otherwise-identical code paths: measure the *full* bounding box of the animating element on video, not just the one axis you assume is moving — the x-only measurements looked perfectly clean through two entire rounds of misdiagnosis.

## Blur/glass specific

- **`NSVisualEffectView`'s blur radius is fixed by its material and isn't a public API.** No amount of `.opacity()` tuning can push diffusion strength past what that fixed radius produces — this is why the widget kept reading "weaker" than Notification Center's own widgets no matter how much the opacity was cranked. The only way past it was to stop using `NSVisualEffectView` for the strength-critical path and do the blur manually: `CGWindowListCreateImage` + `CIGaussianBlur`, on a timer, with a radius we actually control (`DesktopBackdropCapture`).
- **Stacking a SwiftUI `.ultraThinMaterial` on top of a live blur, to try to add extra diffusion, was a mistake.** Material renders its own light-appearance fill *underneath* the blur it's compositing, which washed the whole panel toward opaque white, killed the digit cards' contrast against it, and even reintroduced a corner seam (its clip didn't line up with the layer-masked blur beneath it). Reverted. If more diffusion is ever needed again, the direction is a *stronger blur radius* in `DesktopBackdropCapture`, not a second stacked SwiftUI effect.
- **The native window shadow follows the window's rectangular backing bounds, not a rounded-rect SwiftUI clip inside it.** With the glass panel opaque enough to matter, that mismatch showed as a faint straight edge poking out past all four rounded corners. Fixed by turning `NSWindow.hasShadow` off entirely and letting `WidgetGlassBackground`'s own SwiftUI `.shadow()` (applied after its `clipShape`) do the job — it's naturally shaped correctly since it's computed from the already-clipped content.
- **Corner rounding needs to live on the actual layer doing the compositing, not a SwiftUI-level clip wrapped around it.** `.clipShape()` around a live `NSVisualEffectView` (or, later, a `GeometryReader`-sized captured image) left a faint antialiasing fringe right at the curve. Masking the `NSVisualEffectView`'s own `CALayer` (`cornerRadius` + `masksToBounds`) — and, as the final belt-and-suspenders fix, also masking the *window's content view* itself to the same rounded rect in `OverlayWindowController` — is what actually gets a clean edge.
- **A captured image rendered at its full bitmap resolution instead of the widget's actual size** when passed through `Image().resizable().aspectRatio(.fill)` inside a `shape -> background -> conditional` chain — the size proposal wasn't actually bounded through that path. Fixed with an explicit `GeometryReader`-driven `.frame(width:height:)` before clipping.

## Verification workflow lessons

- **Trust `xcodebuild`'s `BUILD SUCCEEDED`/`FAILED`, never editor-reported/SourceKit diagnostics.** This codebase has repeatedly shown stale "Cannot find type in scope" errors for types that demonstrably exist and compile fine — a whole-project reindex lag, not a real problem.
- **`strings <binary>` is not a reliable way to verify Swift code was actually compiled in.** It failed to find literal string markers (including ones placed in `applicationDidFinishLaunching`, which unconditionally runs) even right after a clean rebuild. Swift's string literal encoding isn't always found by a naive `strings` scan. Don't use it as a "did my code change actually get compiled" check.
- **Plain `print()` from a GUI app launched via `open -n` doesn't reach a capturable stream.** Redirecting stdout to a file when launching the binary directly produces nothing, even for output that must have run. `NSLog()` does route through unified logging and is capturable via `log show --predicate 'process == "AppName"'` — use that instead. Note also that string-interpolated content in `NSLog` gets redacted as `<private>` in the log; use `%d`/`%@` C-style format specifiers for values you actually need to read back, or just check for the log line's *presence/timing* (which survives redaction) when that's enough signal.
- **Ad-hoc dev code signing changes the app's identity on every rebuild**, so macOS re-prompts for Screen Recording permission after every single `xcodebuild`. This is expected local-dev behavior, not a regression — won't happen with a real signed release build.
- **Synthetic mouse events (`cliclick m:`/`c:`) don't reliably cross `NSTrackingArea` boundaries the way real mouse movement does.** Multiple incremental synthetic moves toward a target still failed to trigger `.onHover` in testing, even when the underlying SwiftUI code was later confirmed correct via a forced-state test. Don't conclude a hover-driven feature is broken purely from a failed synthetic-hover screenshot test — verify the state-driven UI renders correctly when force-set, and treat real-mouse confirmation as a separate, harder-to-automate step.
- **Screenshot automation can capture things it shouldn't.** Mid-session, an automated screenshot captured the user on a live video call with another person visible on screen. Always sanity-check *why* you're taking a screenshot and be ready to stop immediately and flag it if the screen content turns out to be a live personal/video-call context, not the app under test.

## Product decisions

- Compact menu bar rendering is deliberately opaque, never glass — glass at 14×20pt in a status item isn't practical or legible.
- The desktop overlay window intentionally sits below normal app windows (level = desktop-icon level + 1) — matches how system widgets behave, not a bug to "fix" by raising it.
- Popovers ride on the popover's own existing vibrancy (`VibrantHostingController`) rather than getting their own per-card blur panel — there's no meaningful desktop content directly behind a popover window for a `behindWindow` blend to sample, so giving a card its own blur panel there just grays things out flatly.
- The tint/accent-color customization feature was built, then fully removed at the user's explicit request in favor of font customization instead — if tint-like code surfaces again in a diff, it's very likely meant to be *removed*, not extended.
